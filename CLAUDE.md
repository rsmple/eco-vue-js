# eco-vue-js

Vue 3 UI kit published to npm as `eco-vue-js`. Also ships a shared eslint config (`eslint/`) and a Tailwind base (`tailwind-base/`).

## Commit messages

- Changes: `ui-kit: <lowercase summary>` — imperative, lowercase after the prefix, no trailing period.
  - `ui-kit: add default slot to WButtonMoreItem`
  - `ui-kit: fix current-title update in WTabs when header is hidden`
  - `ui-kit: prevent backspace/delete from stripping the line container in ContentEditable`
- Version bumps: the bare version as the entire message — `0.13.6`. Nothing else in that commit but the version bump.
- Several related changes may be squashed into one `ui-kit:` commit with comma-separated clauses:
  `ui-kit: do not refocus input on clear, drop min-width for input with prefix, expose before slot in WInputSuggest`

## Release notes

There is no `CHANGELOG.md` — the [GitHub Releases](https://github.com/rsmple/eco-vue-js/releases) page is the changelog.

- Tag and title are both `vX.Y.Z`.
- Body is 2–4 hand-written consumer-facing bullets, each starting with `- `.
- Write what changed for someone using the component, not what the commit did. Start with a verb (`Add`, `Fix`, `Expose`, `Drop`, `Move`) and name the component.
- Markdown is rendered, so use it:
  - Backticks for props, slots, emits, classes, packages and rule namespaces — `` `submitText` ``, `` `no-header` ``, `` `mb-4` ``, `` `import-x/` ``.
  - `**Breaking**: ` as a bold lead-in for breaking changes.
  - An em-dash clause to add the mechanism or consequence after the main statement.
  ```
  - Add `submitText` and `disableMinHeight` props to WModalStepper
  - Fix `update:current-title` in WTabs not emitting the initial title when the header is hidden (`no-header`) — the title is now watched directly instead of relying on tab activation
  - **Breaking**: eslint config now uses eslint-plugin-import-x — rule namespace changed from `import/` to `import-x/`
  ```
- Component names stay bare (WTabs, WModalStepper), not in backticks.
- Internal-only churn (dependency bumps, lint config, build tweaks) can be a single summary bullet or omitted.

## Release flow

Creating the GitHub release is what publishes to npm — `.github/workflows/npm-publish.yml` runs on `release: created` and does `npm run build` then `npm publish` from `package/`. So the build must be green *before* the release is created.

`package/package.json` is generated by the build from the root `package.json` — never edit it directly.

The full procedure — baseline check, build gate, bump, publish verification and failure recovery — is the `release-ui-kit` skill (`~/.claude/skills/release-ui-kit/`). Follow it rather than improvising the steps.
