# Migrating a consumer to eco-vue-js with Tailwind v4

This release moves the ui-kit's Tailwind base from v3 to v4. **A v4 base cannot be
consumed by a v3 app and vice versa**, so the kit and every consumer have to move
in the same release — there is no gradual path.

Read the [Fails silently](#fails-silently) section first. Most of the work here is
mechanical, but six of the changes produce **no build error** — they either emit CSS
the browser then throws away, or quietly stop emitting a class at all. Those are the
ones that will reach production if you only check that the build is green.

Migrate in dependency order. A consumer that pulls in a sibling package's prebuilt
`dist` (`@whitespots/auditor`) inherits that package's v3 spellings, and no amount of
work in the consumer will fix them.

To verify against unpublished siblings, both local tarballs have to go in through a
**single** `npm i`. The per-package `ui-kit` / `auditor` scripts each run their own
`npm i --no-save`, which re-resolves the tree from `package.json` and drops whatever the
previous one installed — so running them in sequence leaves you with only the last.
`appsec-portal-app/front` has a `local` script that packs both and installs them
together; copy it if your repo needs the same.

```bash
grep -rohE "[a-zA-Z0-9:_-]+-\[--[^]]+\]" src | wc -l
grep -rohE "(^|[\"'\` :])-[a-z][a-z0-9-]*--[a-z]" src | wc -l
```

**The `-prop--key` column above badly undercounts.** It was measured with a grep
whose boundary was only `["' ]`, which misses every variant-prefixed occurrence —
and those are the bulk of them. `appsec-portal-app/front` measured 51 that way and
actually needed 335, of which `sm-not:-px--inner-margin` alone was 141. The grep
here uses the wider boundary; trust it over the table.

## Fails silently

### 1. `[--var]` is no longer shorthand for `var(--var)`

The single highest-risk change. In v3, `rounded-[--w-input-rounded,0.75rem]` expanded
to `var(...)`. v4 takes the brackets literally, so **the class is still generated** and
the declaration is still written — with a value the browser discards:

```css
/* v3 */  border-radius: var(--w-input-rounded,0.75rem);   ✓
/* v4 */  border-radius: --w-input-rounded,0.75rem;        ✗ invalid, dropped
```

The v4 form is parentheses, which emits byte-identical CSS to v3:

```diff
- class="rounded-[--w-input-rounded,0.75rem] bg-[--w-input-bg,inherit]"
+ class="rounded-(--w-input-rounded,0.75rem) bg-(--w-input-bg,inherit)"
```

Only brackets whose content *starts with* `--` are affected. Leave
`max-h-[calc(100%-var(--inner-margin,0px))]` alone — that is a normal arbitrary value.

### 2. Two spellings for CSS-variable size keys

`tailwind-base/theme/sizes.ts` registers keys that are themselves custom properties
(`--inner-margin`, `--header-height`, `--w-option-padding`, …). The canonical class is
`{prop}---{key}` — three dashes. v3 also matched a two-dash spelling and emitted a
**positive** value for it; v4 emits nothing at all.

```diff
- class="-px--inner-margin -h--header-height"
+ class="px---inner-margin h---header-height"
```

Utilities that genuinely negate already have three dashes (`-mr---inner-margin`) and
are **unchanged** — do not touch those. The codemod below distinguishes them.

### 3. Variants no longer apply to `addBase`

If you have your own plugin registering classes via `addBase`, variants of those
classes (`hover:`, `after:`, `disabled:`) were generated by v3 and are **not**
generated by v4. Move anything that needs variants to `addUtilities`.

This bit the kit itself: `text-accent`, `text-description` and `w-skeleton-static`
are now `addUtilities`. Check your local plugins for the same pattern — and note
that the bare class keeps working, so only the *variant* forms vanish.

To find them mechanically, list the class names your plugins register under
`addBase` and grep the consuming source for `<variant>:<class>`.

### 4. A bare custom property in an arbitrary *property* value

The sibling of failure 1, and not caught by its codemod. v3 also expanded a value
that started with `--` inside an arbitrary property:

```css
/* from `[grid-template-areas:--w-list-grid-areas]` */
/* v3 */  grid-template-areas: var(--w-list-grid-areas);   ✓
/* v4 */  grid-template-areas: --w-list-grid-areas;        ✗ invalid, dropped
```

There is no paren shorthand here — the value has to be spelled `var(...)`:

```diff
- class="[grid-template-areas:--w-list-grid-areas] [stroke-width:--w-svg-stroke,2px]"
+ class="[grid-template-areas:var(--w-list-grid-areas)] [stroke-width:var(--w-svg-stroke,2px)]"
```

This applies to custom-property targets too — `[--w-list-left:--w-list-header-rounded,1rem]`
becomes `[--w-list-left:var(--w-list-header-rounded,1rem)]`.

```bash
grep -rnE "\[[a-zA-Z-][a-zA-Z0-9-]*:--" src
```

### 5. Colours in a plugin `theme` are **not** flattened

v4 flattens the `--color-*` namespace only for colours declared in CSS via
`@theme`. Colours declared in a plugin's `theme` — which is how this base and most
consumers declare theirs — keep whatever nesting they are written with, and
`theme('colors')` hands that nesting straight through.

So a nested group registers one utility taking an object and none of the per-shade
utilities. `matchUtilities` reports nothing; the classes are simply absent:

```diff
- gray: {...colors.gray, 850: '#1c1e26'},   // yields `*-gray`, never `*-gray-400`
+ ...shades('gray', {...colors.gray, 850: '#1c1e26'}),
```

v3 papered over this with `flattenColorPalette`, which v4 removed. Declare every
palette flat, and remember that dotted lookups have to follow:
`theme('colors.gray.400')` → `theme('colors.gray-400')`.

### 6. Commas no longer separate grid tracks

By count this is the largest change in the migration — 246 occurrences in
`appsec-portal-app/front` alone.

v3 rewrote every **top-level** comma in a `grid-cols-[…]` / `grid-rows-[…]` arbitrary
value to a space. v4 does not, and a comma-separated track list is not valid CSS, so
the class is still generated and the declaration is still dropped:

```css
/* from `grid-cols-[1fr,auto]` */
/* v3 */  grid-template-columns: 1fr auto;   ✓
/* v4 */  grid-template-columns: 1fr,auto;   ✗ invalid, dropped
```

The separator is the underscore, which v3 accepted too — the fixed form emits
byte-identical CSS on both versions:

```diff
- class="grid-cols-[1fr,auto] grid-rows-[var(--header-height),1fr]"
+ class="grid-cols-[1fr_auto] grid-rows-[var(--header-height)_1fr]"
```

There is no flag to restore the v3 behaviour — the rewrite was hard-coded into those
two utilities and is gone.

**Only top-level commas move.** Commas inside `repeat()`, `minmax()` or a `var()`
fallback are real CSS and v3 left them alone as well, so rewriting them breaks the
value. Both kinds routinely appear in one class:

```diff
- grid-cols-[var(--actions-bar-filter-width-current,0),var(--w-actions-bar-width)]
+ grid-cols-[var(--actions-bar-filter-width-current,0)_var(--w-actions-bar-width)]
```

`repeat(auto-fill,minmax(var(--w-list-card-width,16rem),1fr))` has no top-level comma
at all and is **unchanged**. The codemod tracks paren depth for exactly this reason —
a blind `,` → `_` is wrong on roughly a fifth of the hits.

The rewrite was specific to these two utilities. `shadow-[…]`, `transition-[…]` and
arbitrary properties like `[grid-template-columns:1fr,auto]` all passed commas through
verbatim in v3 as well, so they need no change — and an arbitrary property spelled
that way was already broken before the migration.

### 7. Hand-written gradients lose their direction

v3 kept the gradient direction outside the stops variable, so a class could set
`--tw-gradient-stops` to colours alone and pair with any `bg-gradient-to-*`:

```css
/* v3 */  .bg-gradient-to-bl { background-image: linear-gradient(to bottom left, var(--tw-gradient-stops)) }
/* v4 */  .bg-gradient-to-bl { --tw-gradient-position: to bottom left in oklab;
                               background-image: linear-gradient(var(--tw-gradient-stops)) }
```

v4 folds the direction **into** the variable, as its first value. A colours-only
override is still valid CSS — `linear-gradient(#a, #b, #c)` — so nothing errors; the
gradient just silently renders top-to-bottom. Prepend the position:

```diff
  '.wrt-gradient-stops': {
-   '--tw-gradient-stops': `var(--wrt-from, …), var(--wrt-via, …), var(--wrt-to, …)`,
+   '--tw-gradient-stops': `var(--tw-gradient-position), var(--wrt-from, …), var(--wrt-via, …), var(--wrt-to, …)`,
  }
```

The same applies to a rule that hand-writes the whole declaration:

```diff
  .gradient-primary {
-   background-image: linear-gradient(120deg, var(--tw-gradient-stops));
-   @apply from-[#B376FA] via-[#ac99eb] to-[#827BFF]
+   @apply bg-linear-[120deg] from-[#B376FA] via-[#ac99eb] to-[#827BFF]
  }
```

```bash
grep -rn "tw-gradient-stops" src tailwind
```

Note `bg-gradient-to-*` still works — v4 keeps it as an alias of `bg-linear-to-*` — so
there is no need to rename the ~20 call sites a typical front has. Both spellings now
interpolate `in oklab` rather than sRGB, which shifts midpoints very slightly.

## Steps

### 1. Dependencies

```bash
npm rm autoprefixer postcss-import
npm i -D tailwindcss@4 @tailwindcss/vite@4
```

`@tailwindcss/postcss` is only needed if you are not on Vite. `postcss-import` and
`autoprefixer` are both built into v4 — keeping them causes double processing.

### 2. Vite config

```diff
- import autoprefixer from 'autoprefixer'
- import postcssImport from 'postcss-import'
- import tailwindcss from 'tailwindcss'
+ import tailwindcss from '@tailwindcss/vite'

  export default defineConfig({
-   plugins: [vue()],
-   css: {
-     postcss: {
-       plugins: [postcssImport(), tailwindcss({config: './tailwind/tailwind.config.ts'}), autoprefixer()],
-     },
-   },
+   plugins: [tailwindcss(), vue()],
  })
```

### 3. Delete `tailwind/tailwind.config.ts`

v4 has no presets and no `content` array. Everything moves into your CSS entry point.
Do **not** keep the config and load it with `@config` — nested colours behave
differently under it (see step 5) and you would be migrating twice.

### 4. CSS entry point

Replace the `@tailwind` directives:

```diff
- @tailwind base;
- @tailwind utilities;
- @tailwind components;
+ @import "tailwindcss";
+ @import "eco-vue-js/tailwind-base/base.css";
+
+ /* one @source per extra scanned package, replacing the old `content` entries.
+    Paths are relative to THIS file, not to the project root. */
+ @source "../../../node_modules/@whitespots/auditor/dist";
```

**Any *other* CSS entry point that uses `@apply` needs `@reference`.** A second
stylesheet imported from `main.ts` is compiled on its own and has no theme in
scope, so every `@apply` in it fails the build with `Cannot apply unknown utility
class`. Point it at the entry above — nothing is emitted twice:

```diff
+ @reference "./styles.css";

  .w-markdown h1 { @apply font-medium }
```

The same applies to SFC `<style>` blocks, if you have any.

`eco-vue-js/tailwind-base/base.css` replaces both `presets: [tailwindBase]` and the
`...tailwindBase.content` spread — it declares its own `@source` internally, so you no
longer need a path into `node_modules/eco-vue-js`.

Your own `src` needs no `@source`: v4 auto-detects sources from the project root.

**`@source` is required for any scanned package**, though — auto-detection skips
gitignored paths, and `node_modules` is gitignored. Without an explicit `@source`, a
dependency's classes are silently absent. Note the path is resolved relative to the CSS
file that declares it, so from `src/assets/styles/index.css` you need to climb three
levels.

### 5. Theme → `@theme`, and colours go flat

There is no nesting in v4 — the `--color-*` namespace is flat. A nested group like
`scanner: {secrets, sast, …}` must be written out:

```diff
- colors: {
-   scanner: {
-     secrets: '#4f46e5',
-     'secrets-dark': '#818cf8',
-   },
- },
+ @theme {
+   --color-scanner-secrets: #4f46e5;
+   --color-scanner-secrets-dark: #818cf8;
+ }
```

Repos with nested groups to flatten: `appsec-portal-app` (`scanner`),
`traio-project` (`black`, `gray`, `severity`, `score`, `scanner`),
`whitespots-io` (`site`, `gray`, `scanner`).

Everything else maps to a namespace:

| v3 `theme` key | v4 namespace |
|---|---|
| `colors` | `--color-*` |
| `fontFamily` | `--font-*` |
| `fontSize` | `--text-*` |
| `screens` | `--breakpoint-*` |
| `borderRadius` | `--radius-*` |
| `boxShadow` | `--shadow-*` |
| `dropShadow` | `--drop-shadow-*` |
| `keyframes` / `animation` | `--animate-*` |
| `spacing`, `width`, `height`, `padding`, `margin`, `gap`, `inset` | all derive from `--spacing` |

Var-valued colours work unchanged: `--color-wrt-to: var(--wrt-to);`.

Local plugins can stay JavaScript — `@plugin "./plugins/default.ts"`. The v4 plugin API
still has `addVariant`, `matchVariant`, `matchUtilities`, `addUtilities`, `addBase`,
`theme()`. `.ts` plugin files load without a build step. Two v3 imports inside them
have no v4 equivalent and are re-exported by the kit instead:

```diff
- import flattenColorPalette from 'tailwindcss/lib/util/flattenColorPalette'
+ import {colorValues} from 'eco-vue-js/tailwind-base/utils.js'

- {values: flattenColorPalette(theme('colors'))}
+ {values: colorValues(theme('colors'))}
```

```diff
+ import {DARK_SELECTOR} from 'eco-vue-js/tailwind-base/constants.js'

- [config('darkMode')[1][0]]: {'--wrt-to': theme('colors.gwrt-to-dark')},
+ [DARK_SELECTOR]: {'--wrt-to': theme('colors.gwrt-to-dark')},
```

`config()` is gone entirely — there is no v4 config to read the dark selector back
out of. Delete the `tailwindcss/lib/util/flattenColorPalette` module declaration
from `env-node.d.ts` too, if you have one.

Two things a plugin **cannot** do, so they must be in CSS:

- reset a namespace — a plugin `theme` always merges with the defaults rather than
  replacing them, so reproducing a v3 non-`extend` `theme.colors` needs
  `@theme { --color-*: initial; }`
- declare `@source`

### 6. Run the codemods

Save as `codemod.mjs` in the repo root and run `node codemod.mjs`. Commit first — it
edits in place.

```js
import {readFileSync, writeFileSync} from 'node:fs'
import {execSync} from 'node:child_process'

// `.css` matters: an entry point's `@apply` lists carry the same v3 spellings.
const files = execSync(`find src -type f \\( -name '*.vue' -o -name '*.ts' -o -name '*.css' \\)`, {encoding: 'utf8'})
  .split('\n').filter(Boolean)

// 1. `[--var]` shorthand -> `(--var)`. Only brackets starting with `--`;
//    `[calc(100%-var(--x))]` must be left alone.
const VAR_SHORTHAND = /-\[(--[^\][]*)\]/g

// 2. `-px--inner-margin` -> `px---inner-margin`. The `:` in the boundary catches
//    variant-prefixed occurrences (`sm:-left--left-inner`), the `!` catches v3
//    important (`!-min-h--height-inner`). Genuine negatives already have three
//    dashes, so the `(?=[a-z])` lookahead skips them.
//
//    The property is matched generically rather than from a fixed list — every
//    hand-written list of these has turned out to be missing something
//    (`gap-x`, `gap-y`, `w-button-h`, `w-skeleton-w` were all absent from the
//    first one), and a miss is silent.
const SLOPPY = /(^|[\s"'`:!])-([a-z][a-z0-9-]*?)--(?=[a-z])/g

// 3. `[display:block!important]` -> `[display:block]!`
const IMPORTANT = /-\[([^\][]*?)!important\]/g

// 4. `[prop:--var]` -> `[prop:var(--var)]`, including custom-property targets.
//    There is no paren shorthand for arbitrary-property values.
const ARBITRARY_PROP = /\[((?:--)?[a-zA-Z-][a-zA-Z0-9-]*):(--[^\]()]*)\]/g

// 5. `grid-cols-[1fr,auto]` -> `grid-cols-[1fr_auto]`. Regex alone cannot do this:
//    only commas at paren depth 0 are separators, so the value is walked instead.
const GRID = /\bgrid-(cols|rows)-\[([^\][]*)\]/g

let a = 0, b = 0, c = 0, d = 0, e = 0, touched = 0

const gridTracks = (value) => {
  let depth = 0, out = ''

  for (const char of value) {
    if (char === '(') depth++
    else if (char === ')') depth--
    else if (char === ',' && depth === 0) { e++; out += '_'; continue }
    out += char
  }

  return out
}

for (const file of files) {
  const before = readFileSync(file, 'utf8')
  let after = before.replace(VAR_SHORTHAND, (_m, v) => { a++; return `-(${v})` })
  after = after.replace(SLOPPY, (_m, pre, prop) => { b++; return `${pre}${prop}---` })
  after = after.replace(IMPORTANT, (_m, v) => { c++; return `-[${v}]!` })
  after = after.replace(ARBITRARY_PROP, (_m, p, v) => { d++; return `[${p}:var(${v})]` })
  after = after.replace(GRID, (_m, axis, v) => `grid-${axis}-[${gridTracks(v)}]`)

  if (after !== before) { writeFileSync(file, after); touched++ }
}

console.log(`  [--var] -> (--var)        : ${a}`)
console.log(`  -prop--key -> prop---key  : ${b}`)
console.log(`  [x!important] -> [x]!     : ${c}`)
console.log(`  [p:--v] -> [p:var(--v)]   : ${d}`)
console.log(`  grid track , -> _         : ${e}`)
console.log(`  files changed             : ${touched}`)
```

Rule 5 runs last so it sees the `(--var)` output of rule 1 — a value rewritten to
`grid-cols-(--a,--b)` has no brackets and is correctly left alone.

The `!`-prefix important form is otherwise unhandled — rule 2 only fixes it where
it coincides with a sloppy key. Sweep the rest by hand; `grep -rnE "[\"' ]![a-z]" src`
finds them, but most hits are JS negations, so check each one.

**Re-run the codemods after every merge from `develop`.** Any branch cut before the
migration keeps writing v3 spellings, and they come back in silently — on
`appsec-portal-app/front` a selection-scope branch reintroduced 35 sloppy size keys and
all 246 grid commas after the migration commit had already landed.

### 7. Manual conversions

**Opacity utilities are gone.** Fold the value into the colour with `/N`. You have to
find the paired colour on the same element — this is why it is not a codemod:

```diff
- class="bg-black-default hover:bg-opacity-5"
+ class="hover:bg-black-default/5"

- class="bg-default dark:bg-default-dark"
- :class="{'supports-backdrop:bg-opacity-40 supports-backdrop:dark:bg-opacity-60': isTransparent}"
+ class="bg-default dark:bg-default-dark"
+ :class="{'supports-backdrop:bg-default/40 supports-backdrop:dark:bg-default-dark/60': isTransparent}"
```

`*-opacity-100` is a no-op — just delete it.

**Opacity over a dynamic colour has no direct equivalent.** If you use
`border-opacity-0` to hide a border whose colour is set by a *different, conditional*
class, there is no v4 utility for it — nothing can modify the alpha of a separately
declared colour. Route the colour through a CSS variable and toggle the variable
instead. The kit hit this in `WInput` (seamless borders).

**Important moved from prefix to suffix**: `!flex` → `flex!`.

### 8. Utility renames

Mostly handled by the [official upgrade tool](https://tailwindcss.com/docs/upgrade-guide),
which is worth running for these before the codemods above:

| v3 | v4 |
|---|---|
| `shadow-sm` / `shadow` | `shadow-xs` / `shadow-sm` |
| `rounded-sm` / `rounded` | `rounded-xs` / `rounded-sm` |
| `blur-sm` / `blur` | `blur-xs` / `blur-sm` |
| `drop-shadow-sm` / `drop-shadow` | `drop-shadow-xs` / `drop-shadow-sm` |
| `outline-none` | `outline-hidden` |
| `ring` | `ring-3` |
| `flex-shrink-*` / `flex-grow-*` | `shrink-*` / `grow-*` |
| `overflow-ellipsis` | `text-ellipsis` |
| `decoration-slice` / `decoration-clone` | `box-decoration-slice` / `box-decoration-clone` |

Note the upgrade tool does **not** catch the three silent changes at the top of this
document.

## Unchanged — do not "fix" these

- **Dark mode.** The kit still registers `dark` as `.dark &:not(:is(.light *))`, so
  `.light` subtrees (printable pages) keep opting out of dark mode. Emitted selectors
  are identical to v3.
- **`-not` breakpoints.** `sm-not:`, `xl-not:` and the rest work as before, along with
  the custom `xs` / `3xl` / `4xl` / `5xl` breakpoints.
- **All `w-*` variable utilities** — `w-input-bg-*`, `w-skeleton-rounded-*`,
  `w-ripple-opacity-*` etc. — generate from your palette exactly as before, including
  colours you define yourself.
- **Named groups** (`group/seamless`, `group-hover/seamless:`) work; v4 just no longer
  emits an empty rule for the marker class.

## Also worth knowing

- **`tailwindcss/colors.js` now returns oklch, not hex.** Built-in `gray` / `slate`
  shift very slightly. More importantly, any code doing string concatenation on a theme
  colour (`` `${theme('colors.positive')}4d` `` for alpha) breaks for oklch values — use
  `color-mix()` or a `/N` modifier.
- **Container queries are built in.** The kit's custom plugin is gone. `@sm:` is
  unchanged; `@not-lg:` becomes `@max-lg:`.
- **`eslint-plugin-tailwindcss` moves to 4.x**, which is a rewrite made for Tailwind v4.
  It comes in through the kit's `eslint/configs/configTailwind.js`, so you get it with
  the version bump — nothing to install. Three things changed for consumers:

  - **`cssConfigPath` is mandatory.** v4 has no JS config to discover, so the plugin has
    to be pointed at your CSS entry point. `configTailwind` defaults to
    `src/assets/styles/styles.css` — the path every front already uses. If yours differs,
    pass it through:

    ```diff
      ...recommended({
    +   cssConfigPath: 'src/styles/app.css',
        tsConfig: './tsconfig.json',
      })
    ```

    A relative path is resolved from the nearest `eslint.config.*` or `package.json`
    *above the linted file*, not from the project root — in a repo with a nested
    `package.json` this silently picks the wrong base and lint dies with `ENOENT`. Pass
    an absolute path (`path.join(import.meta.dirname, …)`) if that applies to you.

  - **`migration-from-tailwind-2` is gone**; remove it if you override it anywhere.
    New rules `important-modifier-suffix` (catches v3's `!flex`, which v4 spells `flex!`)
    and `no-unnecessary-arbitrary-value` are on as warnings.

  - **`classnames-order` is off** in the kit config. v4 sorts differently enough from v3
    that leaving it on flags essentially every class attribute — 1537 warnings in the kit
    alone — and auto-fixing would rewrite class attributes across every repo. Not worth
    bundling into the migration diff.

  `no-contradicting-classname` is an error and does now fire correctly under v4, which
  is how `focus-within:outline focus-within:outline-2` in WInput was found — v4's
  `outline` sets a width, so it conflicts with `outline-2` where v3's did not. Expect a
  small number of genuine hits in your own code (`appsec-portal-app/front` had two).

  The fix is to **drop the bare `outline`**: in v4 `outline-<n>` sets the style as well,
  so `outline-4` alone is what `outline outline-4` meant in v3. Leaving both in place is
  not cosmetic — each sets `outline-width`, so which one wins depends on their order in
  the emitted sheet rather than on the class list.
- **Padding/margin now emit logical properties** (`padding-inline` rather than
  `padding-left` + `padding-right`). Only matters if you override them by property name.

## Verifying

A green build proves very little here — the silent failures all compile. Check the
output CSS:

```bash
# 1. no literal custom-property values left (failure modes 1 and 4).
#    Note the built CSS is minified onto a few long lines, so `grep -c` counts
#    LINES, not occurrences, and will happily report "1" for ten distinct bugs.
#    Print them instead:
find dist -name '*.css' -exec cat {} + | grep -oE "[;{][a-z-]+:\s*--[a-z][a-z0-9-]*[^;}]*" | sort -u

# 2. no comma-separated grid track lists left (failure mode 6). A comma that is
#    still inside repeat()/minmax()/var() is fine, so print and eyeball rather
#    than count — `repeat(auto-fill,minmax(16rem,1fr))` is a legitimate hit.
find dist -name '*.css' -exec cat {} + | grep -oE "grid-template-(columns|rows):[^;}]*" | grep , | sort -u

# 3. classes you expect are actually generated
grep -c 'rounded-\\(--w-input-rounded' dist/**/*.css
```

Then compare the generated class set against the v3 baseline. Build the old CSS on the
pre-migration commit, build the new one, extract the class names from each, and diff —
that is what surfaced every issue in this document.

A `git worktree` at the pre-migration commit is the cheapest way to get the baseline —
`npm ci` there, `npm run build-only` (skip `type-check`), and keep the emitted CSS.
**Sort both class lists with the same collation.** Extracting with one tool and
comparing with `comm` under a different one produces a diff that is wrong in both
directions, and it fails quietly — it under-reports real regressions rather than
erroring. Pipe both through `LC_ALL=C sort -u`.

The diff is large and mostly noise, so classify it rather than reading it. For each
class present in v3 but not v4, grep the *sources* (your `src`, plus the scanned
`node_modules` packages) for that class as a **whole delimited token** — `bg-gray-800`
must not match inside `dark:bg-gray-800`. A class still present in source is a real
regression; everything else is a v3 scanner artefact. On `appsec-portal-app/front`
that reduced 232 dropped classes to about a dozen worth looking at, and it is how the
`addBase` variant loss and the arbitrary-property bug were both found.

Two categories of "real" hit are nonetheless fine: a class only ever used in an
`@apply` (v3 emitted the standalone utility as well, v4 inlines it and stops there),
and anything coming from a **sibling package that has not been migrated yet** — its
prebuilt `dist` still ships v3 spellings and will keep failing silently until that
repo is migrated and republished. Migrate and rebuild the leaf packages first.

Expect the v4 set to be *smaller*:
v3's scanner split candidates on `:` and emitted unused bare utilities (`animate-pulse`
alongside `before:animate-pulse`), and it also generated rules for false positives
picked out of JavaScript — Vue props like `:align-top`, variables like `collapseList`,
negations like `!outline`. Those disappearing is correct.

Finally, click through in a browser with dark mode toggled. The silent failures are
dropped declarations, so they show up as layout and colour regressions, not as errors.
